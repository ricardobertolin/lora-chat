Section 1

System Overview

Two radios, two devices, no infrastructure
Description

LoRa Chat is a point-to-point messaging system built from two Heltec WiFi LoRa 32 (V3) boards. Each board is a dumb radio pipe: it carries newline-delimited text and reports what it hears. All protocol, encryption, positioning and measurement live in a browser application.

The consequence is that most changes require no reflashing. Position sharing, encryption, media transfer and delivery receipts were all added without touching the firmware.

Features
  • Text messaging with delivery receipts
  • AES-256-GCM encryption, passphrase derived
  • Position sharing and a north-up radar
  • Link measurement: delivery ratio and margin
  • Image and audio transfer
  • Radio settings changed at runtime, with rollback
  • Runs offline as an installed web application

Signal Path

[ browser ] [ browser ] | | USB serial USB serial | | [ ESP32-S3 ] [ ESP32-S3 ] | | SPI @ 8MHz SPI @ 8MHz | | [ SX1262 ] ))) - - - - LoRa 915 MHz - - - - ((( [ SX1262 ] 1.25 kbit/s at SF9

The link carries 1.25 kbit/s at the default settings. Every feature in this manual is constrained by that figure; where a feature costs meaningful airtime it is stated in the relevant section.

IMPORTANT: The radio measures nothing about distance. The SX1262 has no ranging engine. All distances reported by the application are computed from shared GPS coordinates and transmitted as ordinary messages.

Description

Dual-core ESP32-S3 with 8 MB embedded flash, an SX1262 sub-GHz transceiver, a 128x64 SSD1306 display and a CP2102 USB bridge. The 863-928 MHz variant covers both EU868 and AU915 plans.

Firmware Reference

lora_chat.ino  /  115200 8N1

The firmware exchanges lines of text over USB serial. A line typed in is transmitted; a line received is printed with its signal figures. Everything else is the application's business.

Serial Output Format

PrefixMeaningExample
===Boot banner, carries the node name=== LoRa chat - this board is "8424" ===
>>Transmitted. Printed once on air.>> hello
<<Received, with RSSI and SNR<< 3D2C: hi (RSSI -44.0 dBm, SNR 11.2 dB)

NOTE: The >> echo is printed only after the packet is actually on the air. The application uses it as flow control when sending fragments; a fixed delay would overrun the 256-byte serial buffer.

Line Limits

LimitValueNotes
Serial input line200 charsOverflow is transmitted as a second packet

IMPORTANT: A line over 200 characters is split silently. Encrypted, the ciphertext is cut and neither half authenticates, and the receiver reports a passphrase mismatch. The application fragments anything longer rather than submitting it; see Section 8.

Node Naming

Each board names itself from the last two bytes of its MAC address, giving a four-character hexadecimal identifier such as 8424. The name is prefixed to every transmission. Operator-facing nicknames are an application concern and do not change this identifier.

Change Sequence

Both ends must agree on every parameter, so a change is never applied alone:

  1. The new settings are broadcast on the old ones, while the other board can still hear.
  2. Both ends apply them and each arms a 30-second rollback.
  3. Each transmits a probe after a randomised 300-1200 ms delay. Receiving anything confirms the change and disarms the rollback.
  4. If nothing arrives within 30 seconds the previous settings are restored automatically.
NOTE: The probe delay is randomised because two boards switching at the same instant would otherwise transmit over each other, both hear silence, and both roll back a change that was sound.
CAUTION: Regional limits are the operator's responsibility. 915 MHz suits Brazil and AU915 plans; use 868.0 where EU868 applies.

Presence

Raw LoRa has no association step; anyone on the same frequency and sync word hears everything. Presence is therefore inferred. Any traffic counts as a sign of life. Five minutes of silence marks a node quiet; it is greyed rather than removed, because on this link a node that has left and one that is behind a hill look identical.

Outbox

Messages typed while disconnected, or unacknowledged after their window, are held and sent once a board is attached. Capacity is 50; past that the oldest is dropped rather than refusing new ones. The composer remains usable with no board present.

Link Measurement

Margin, not signal strength
IMPORTANT: Received signal strength is a misleading measure of link health. It is observed only for packets that arrived, so at the edge of range the weak ones vanish and the average improves. A link appears healthiest immediately before it fails.

LoRa demodulates below the noise floor, so signal-to-noise ratio against the spreading factor's limit predicts success far better. Margin is the headline figure:

margin = SNR - floor(SF)
range multiplier = 10 ^ (margin / (10 * n))
  where n is the path-loss exponent:
  2 free space, 3 suburban, 4-6 dense urban

Demodulation Floors

Measurement Procedure

The following invalidate a measurement if ignored:

  • Antenna orientation. Both vertical. Cross-polarisation can cost 20 dB, more than the entire SF7 to SF12 range.
  • Height. Waist or above. Ground proximity obstructs the Fresnel zone; on the pavement is easily 10 dB down.
  • Body position. 900 MHz is absorbed by the operator. Keep posture consistent between readings.
  • Sample count. Twenty probes minimum per point. Fading makes a single sample meaningless.
  • Fixed power. Set it explicitly, or readings are not comparable.

Delivery ratio excludes probes still within their timeout. Counting them as lost would make the figure dip after every transmission.

Media Transfer

Fragmentation, dithering, ADPCM

Encoding

TypeEncodingSizeAt SF9
Image 128x641-bit Floyd-Steinberg1 kB~15 s
Image 192x1441-bit Floyd-Steinberg3.4 kB~50 s
Audio 4 kHz4-bit IMA ADPCM2 kB/s~30 s per second
Long textUTF-8, fragmentedas typedproportional

Dithering rather than a threshold: at one bit a threshold destroys every gradient in the image. The sender is shown the dithered result before it is transmitted.

Transfer Sequence

  1. The blob is encrypted once as a whole, not per fragment.
  2. It is base64 encoded and split into fragments of at most 180 characters.
  3. Fragments are transmitted one at a time, paced by the board's echo.
  4. !BE marks the end. The receiver requests anything missing.
  5. Three resend rounds, then the transfer is abandoned.
NOTE: Per-fragment encryption would add 28 bytes plus base64 expansion to every line and roughly halve throughput. The cost of encrypting once is that fragment headers travel in the clear - sequence numbers and a one-letter type, no more than the node name already reveals.
CAUTION: A transfer occupies the channel for its full duration. Nothing else can be sent. Reduce the spreading factor with /sf 7 before sending media; it is roughly four times faster than SF9.

Audio Limitations

ADPCM is not a speech codec. It is fixed at four bits per sample, so 4 kHz audio costs 2 kB per second, roughly thirty times slower than real time at SF9. A vocoder such as Codec2, running at 700-1600 bit/s, would be five to twenty times smaller and is the correct solution.

Security

Scope and limitations

Cipher

PropertyValue
AlgorithmAES-256-GCM
Key derivationPBKDF2-SHA256, 200 000 iterations
Initialisation vector96-bit, fresh per message
Authentication128-bit GCM tag
Wire overhead28 bytes, then base64 expansion

A wrong key, a tampered packet or a truncated one fails to decrypt rather than producing plausible output.

LIMITATIONS: The salt is fixed. Both ends must derive the same key having exchanged nothing beforehand, which rules out a per-conversation salt, so the passphrase alone determines the key. Identical passphrases produce identical keys. The iteration count and passphrase strength carry the security.

The following are not concealed: the node name, which the firmware prefixes outside the ciphertext; message timing and length; and the fact that a transmission occurred. Traffic analysis remains possible.

The passphrase is stored in the browser so the application survives a reload. This protects against interception on the air, not against physical access to an unlocked device.

Channel Sharing

A QR code and link carry frequency, spreading factor, bandwidth, power and passphrase. The payload rides in the URL fragment, which browsers never transmit to a server, and is removed from the address bar once applied.

CAUTION: Anyone who photographs the code joins the channel and reads everything on it. Treat it as the password it contains.

Positioning

Satellite positioning requires no internet connection. Network assistance only shortens time to first fix: one to five seconds with assistance, up to several minutes on a cold start without it. Obtain a fix before leaving coverage; cached orbital data remains valid for some hours.

ConditionTypical accuracy
Open sky3 - 10 m
Dual-frequency receiver, open sky1 - 3 m
Urban, tree cover10 - 50 m
IndoorsUnusable

Errors at each end combine in quadrature, so a computed separation carries roughly 7 m of uncertainty regardless of distance. At the ranges this equipment operates over, that is negligible.

NOTE: A desktop computer has no satellite receiver. Its position is entered manually and is therefore exact, and it does not move. This is the preferable arrangement: all positional uncertainty sits at the end that is actually moving.

Diagnostic Output

Set > USB diagnostics reports the application version, the transport in use, whether each browser interface exists, whether the context is secure, and offers a device picker accepting any USB device. If that picker is also empty, the browser can see no USB device at all and the fault is the cable or host mode, not the application.

NOTE: Both ends must run the same application version for newer message types to be understood. The version is printed beside the title.
